## Ticket #94 — CLI clika: métricas de analytika desde el terminal (PR #122)

Flujo aika: start (plan de cierre sobre trabajo previo) → implement (9 commits)
→ self-review doble lente (11 findings) → ship → merge → close.

- **Contexto**: el CLI estaba construido desde el 18-oct en `feat/lyka-94`
  (4 commits) y nunca había salido: la rama quedó 20 commits atrás y sin PR.
  El plan fue de cierre: rebasear, arreglar el drift y llevarlo a review.
- **Qué es**: `make clika` abre un REPL con prompt `> `, autocompletado de
  comandos y de las keys vivas del registry (`prompt_toolkit`), historial en
  `~/.clika_history`, y los comandos `metrica <nombre> [clave=valor ...]`,
  `metricas`, `help` y `exit`. La session lee `DATABASE_URL` del entorno en
  `apps/cli/` (los packages no leen env, boundary intacta).
- **Salida**: markdown (`| campo | valor |`) en vez de tablas `rich`: se lee en
  el terminal y se pega en un issue o planilla sin bordes. `rich` salió de las
  dependencias del CLI.
- **Deploy**: no se despliega. `clika` está en el `dev` group de la raíz; como
  dependencia runtime, `apps/api/Dockerfile` dejaba de construir porque
  `uv sync --frozen --no-dev` necesita `apps/cli` en el contexto. Verificado en
  sandbox: como dev dep la imagen la ignora y el Dockerfile no cambia.
- **Drift del rebase**: el conftest de integración del CLI no creaba
  `f_unaccent`, y desde #115 `alumno.search_term` / `materia.search_term` son
  columnas generadas que la llaman (`ProgrammingError: function f_unaccent(text)
does not exist`). Ahora los dos conftest crean `unaccent` + `F_UNACCENT_SQL`
  antes de `create_all`, y quedó escrito en `CODE_CONVENTIONS`.
- **Nombre**: `lyka` → `clika` a mitad de la tarea, para que se lea como CLI.
  Tocó package, target, CI, docs y el ticket.
- **Self-review**: 11 findings (3 ambos, 2 personal, 6 ponytail). 9 fixeados
  (Ctrl-C durante una métrica, deps de test propias del CLI, `AGENTS.md`
  contradictorio, `.PHONY`, import muerto, case de las keys, `shlex` para
  valores con espacios, tests de session en su archivo, NullPool en el e2e);
  1 dropeado (bump de versión del CLI en el release: no se publica); el 🔴 de la
  imagen de api se resolvió con el dev group en vez de tocar el Dockerfile.
- **Tests**: 41 unit + 1 e2e con testcontainers, `clika` 99% (la única línea sin
  cubrir es el `main()` bajo el guard). CI verde: `CI Gates` 2m44s,
  `codecov/patch` y `codecov/project` pass.

## Ticket #109 — Dependabot para npm, uv, docker y GitHub Actions (PR #126)

Flujo aika: start (2 decisiones) → implement (1 commit + 1 fixup) → self-review
express → ship → merge → close.

- **Contexto**: nada se actualizaba solo; la última CVE de runtime se descubrió
  por mail y el inventario se hizo a mano. De paso apareció que el repo no tenía
  ni Dependabot alerts (`GET /dependabot/alerts` → `403 … disabled`).
- **Qué es**: `.github/dependabot.yml` con seis entries — `npm` en `/`
  (release-it) y `/apps/web`, `uv` en `/`, `docker` en `/apps/api` y
  `/apps/web`, `github-actions` en `/`. Weekly, minors+patches agrupados por
  ecosistema, majors sueltos, `commit-message.prefix: chore(deps)`.
- **Decisiones**: cubrir el lockfile de la raíz, que el ticket no enumeraba ·
  habilitar alerts + security updates post-merge · `chore(deps)` para que
  conventional-changelog parsee los bumps.
- **Por qué `uv` en `/`**: los cuatro miembros comparten el `uv.lock` de la
  raíz; un entry por miembro no encontraría lockfile.
- **No verificable antes del merge**: Dependabot solo lee la config de la rama
  default. La validación local fue parsear el YAML y comprobar que cada
  `directory` tiene su manifest; el AC se mira en Insights.
- **CI**: `CI Gates` 2m46s, `codecov/patch` y `codecov/project` pass.

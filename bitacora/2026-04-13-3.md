### Workspace / configuración

- **`create-ticket`** (global, `~/.claude/skills/`) creado — skill para crear GitHub issues con
  preview obligatorio antes de crear; infiere labels, SP y milestone del contexto; avisa si el ticket
  parece > 8 SP y pregunta si dividir. Se probó en vivo con los 13 tickets de Fase 1.

## Decisiones tomadas

- **Tickets transversales** (back + front juntos por feature): permite avanzar ambas capas en
  paralelo y detectar fricciones en la interfaz temprano. Si se hace todo el backend primero, casi
  seguro hay que volver a modificarlo cuando arranca el frontend.
- **API-first dentro de cada ticket:** el ticket de API CRUDs (#3) va antes que los importadores (#4,
  #5) para tener una base de routing bien definida — los importadores pueden agregar su endpoint en
  contexto ya establecido, y Swagger está disponible desde el inicio.
- **Swagger via `/docs` de FastAPI** (built-in), no embebido en Next.js — sin fricción de
  sincronización adicional para Fase 1.
- **Postman collection trackeada en el repo** (`api/postman/academika.postman_collection.json`) —
  convención: si cambiás un endpoint, actualizás la colección en el mismo PR.
- **Redis no incluido en Fase 1** — no se necesita hasta Fase 3 (cache LLM). Se agrega cuando surge.
- **`create-ticket` con preview obligatorio** — nunca crea el issue directo; si los SP parecen 13+
  informa y pregunta si dividir.
